# HEART HEIST — マウス不要・スマホ対応の設計改訂

改訂日：2026-09-21 ／ 設計版：2 ／ 状態：設計済み・ゲーム本体は未実装

## 1. 改訂の目的

「マウスがなくても開始から脱出まで遊べる」「暗い港でも目的・危険・次の操作が読める」「スマートフォンでは2本の親指で完走できる」を必須条件にする。PC専用の一人称ゲームから、**同じ3D世界をキーボードのみ・マウス併用・タッチで遊ぶゲーム**へ改訂する。

プレイヤーは夜の港で浮遊心臓を盗む回収屋。観察→戦闘／潜入／取引を選択→停電→運搬→船へ接続→自分で操縦して脱出、という体験を維持する。三つの方法、混合ルート、地形、体力・弾薬・敵のルール、心臓の重さと牽引音を共有する。PCとスマホで別ゲームを作らない。

参考資料は、ユーザー提供の `Codex_AI_Game_Development_Playbook.md`。採用する原則は「操作の成立を先に検証」「ゲームルールと表現の分離」「小さな変更と検証記録」「実機で性能評価」。資料内の他ゲームの実績値や例示コード、外部サービス・エンジンの選定は、本作への追加要件とはしない。

今回の成果物はこの仕様・既存設計書への反映・[操作可能な画面見本](design/control-preview.html)。見本ではHUDの状態・端末・文字サイズを比較できる。ゲーム本体のスマホ対応を完了したとは扱わない。

## 3. 操作モードとカメラ

タイトルに「キーボードだけ」「マウス＋キーボード」「タッチ」を明示する。PCの初期フォーカスは「キーボードだけで開始」。タッチ端末にはタッチを初期提案するが、画面幅だけで強制切替しない。選択を保存し、ポーズから変更できる。

一人称カメラを維持する。画面全体を見下ろし型へ変更すると、遮蔽物越しの偵察や既存の潜入ルートが変わるため、この改訂では視点操作と補助を改善する。乗船後は既存の三人称カメラを使用する。視点の揺れは初期OFF。

### キーボードだけの操作

| 行動 | 初期キー | 動作 |
|---|---|---|
| 前後・左右移動 | WASD | カメラ方向を基準。斜め移動を正規化 |
| 左右・上下を見る | 矢印キー | 押している間だけ回転。初期水平100°/秒・垂直70°/秒、設定で調整 |
| 射撃 | J | 押し続けると武器側の発射間隔で射撃。キーリピートに依存しない |
| 狙いの補助／候補切替 | K | 見えている候補へ照準を寄せる。再押下で次候補 |
| 視点を水平へ戻す | L | 垂直角のみ0へ。移動方向は変えない |
| 調べる・話す・拾う・装着・点火 | E | 画面に表示した対象と操作を実行 |
| 走る／しゃがむ | Shift／C | マウス不要・タッチは初期トグル。押下式も設定可能 |
| ジャンプ／近接／装填 | Space／F／R | 既存の意味を維持 |
| 牽引開始・解除／降ろす | T／Q | 対象と実行結果を文字で明示 |
| 補助アクション一覧 | H | ポーズする一覧。装填・近接・運搬操作・設定に到達可能 |
| 船の上昇／下降／加速 | Space／X／Shift | 上下は押している間、加速は既存クールダウンを使う |
| 一時停止／メニューを閉じる | Esc | プレイ停止・押下解除。会話中も安全に戻れる |
| メニュー操作 | Tab、Shift+Tab、Enter、Space | ネイティブボタンの移動・決定。選択肢では上下キーも対応 |

キー割当変更・初期値へ戻す・重複警告を設定に用意する。ゲーム中の矢印とSpaceはページをスクロールしない。メニュー・入力欄へフォーカスがあるときはゲーム操作を送らず、フォーム標準操作を優先する。Shift+Tabは走行トグルに解釈しない。pointer lockが使えなくてもこのモードで完走可能にする。

### 狙い・対象選択の補助

キーボードのみ・タッチで初期ON、マウスでは初期OFF。どのモードでも変更可能。初期調整値は正面20°以内・30m以内・遮蔽なし・生存している敵のみ。中心角→距離→安定IDの順で選択し、対象を枠で示す。回転補助は最大90°/秒とし、手動視点入力を優先する。遮蔽・射程外で即解除し、自動発砲や弾の壁抜けは行わない。タッチでは射撃の押下開始時に候補を選び、押下中に弱い照準補助を適用する。右ドラッグでいつでも補助から外れられる。自動で敵へ向き続ける探索モードは作らない。数値は試遊で調整する設計値であり検証値ではない。

インタラクションは既存の距離条件と遮蔽を守る。視線付近の候補を優先し、候補ゼロでは近くの可視対象に切り替える。壁越し・背後には反応しない。選択した対象名と動詞を表示し、対象に輪郭またはマーカーを出す。押下時に対象ID・有効性を再確認し、選択対象が消えた場合に別の扉や人物へ勝手に実行しない。

## 4. スマホ：2本の親指で遊ぶ

横向きのスマホWebをプレイ対象にする。縦向きでもタイトル・設定・続きからは使用可能。プレイ中に縦へ回転したら保存して停止し、「横向きにすると再開できます」を表示する。横へ戻っても自動再開せず「再開」を押す。ブラウザの強制回転APIには依存しない。

- 左親指：直径112〜144 CSS pxの移動スティック。倒し量で歩行速度を変える。指を離すと停止。走行は近くのトグルボタンで切り替え、外周で意図せず走らない。
- 右親指：操作ボタン以外の右側領域をドラッグして視点移動。大きな「撃つ」ボタンは押しながらドラッグして照準も動かせるため、移動・照準・射撃に3本目の指を要求しない。
- 右の主要ボタンは最大3個：固定位置の「調べる／話す等」、戦闘または運搬の主操作、「しゃがむ／立つ」。主要ボタンは56〜64px、その他も48px以上、間隔8px以上。
- 左側に走行トグルとジャンプ、右側に「ほかの操作」を設置。補助一覧から装填・近接・牽引・降ろすに到達できる。必要に応じて1項目をショートカットに固定できる。
- 左利きプリセットで左右の操作領域を交換する。目的・体力・一時停止の位置は維持する。操作サイズ100〜125%、背景不透明度60〜100%、感度、補助強度を設定できる。収まらないサイズはプレビューで分かるようにし、自動的に配置を組み直す。
- 一時停止・補助一覧・会話はゲーム時間を止める。PCにも同じ一覧を提供する。閉じるだけでは射撃などを起こさない。アクションを選んだ場合だけ再開後に1回実行し、実行条件を再検証する。

### 同じ場所のボタンが状態に合わせて変わる

| 状態 | 主操作1（固定位置） | 主操作2 | 主操作3 | 補助 |
|---|---|---|---|---|
| 探索・戦闘 | 調べる／話す／開ける | 撃つ（押下＋ドラッグ） | しゃがむ／立つ | 装填、近接、ジャンプ、走行 |
| 心臓の前 | 外す→持つ | 撃つ | しゃがむ／立つ | 牽引 |
| 抱えて運ぶ | 船なら装着、それ以外は対象操作 | 牽引に切替 | しゃがむ／立つ | 降ろす。射撃・近接は無効理由を表示 |
| 牽引中 | 船なら装着、それ以外は対象操作 | 牽引を解除 | しゃがむ／立つ | 持ち上げる、装填・近接 |
| 装着直後 | 点火 | 無効 | 無効 | 操縦の短い説明 |
| 飛行 | 上昇（押下＋ドラッグで旋回） | 下降 | 加速 | 左スティック移動、右ドラッグ旋回、指を離すと高度維持 |

牽引中は原則射撃可能という既存ルールを維持する。主要ボタン2が解除に置き換わるため射撃はショートカットまたは補助一覧から選べるようにし、戦闘優先レイアウトでは2を「撃つ」、解除を補助一覧へ移せる。状態が変わったときに同じ指の押下を次の動詞へ引き継がず、一度離してから実行する。

左スティックと右操作のpointerIdは独立管理する。pointercancel、lostpointercapture、背景移行、回転、会話開始で全入力を解除する。スクロール抑止はプレイ面のみ。設定画面のスクロール・拡大やブラウザの操作を全ページで禁止しない。画面端から16px＋safe-areaの余白を確保する。

## 5. 読みやすいUI

夜の青緑・心臓のシアン・警告の琥珀という配色を維持し、文字の背景を不透明な濃色にする。常時の長文と装飾英語を減らし、日本語の動詞を優先する。

| 領域 | 内容と優先順位 |
|---|---|
| 左上 | 現在の目的1つ＋短い補足1行。例「心臓を船へ運ぶ」「東の貨物出口が開いた」 |
| 上部 | 体力・残弾・警戒状態。一時停止は右上。状態は色＋記号＋日本語で表示 |
| 中央 | 小さな照準。対象名と距離は対象付近、操作動詞は固定ボタンにも表示 |
| 下中央 | 通信は最大2行、一度に1件。危険・操作不能理由を優先し、過去ログはポーズで閲覧 |
| 下左右 | タッチ操作領域。PCでは操作ヒントだけに置換 |
| 会話 | 発言・選択肢を大きく表示。背景停止、初期フォーカス、スクロール、戻るを用意 |

本文・ボタンは16px以上、目的は18〜22px、補助情報は14px以上、体力等の数値は22px以上。標準／大きめ（125%）を用意する。通常文字4.5:1以上、主要部品の境界3:1以上を設計上のコントラスト目標にする。大きな文字でも省略してよいのは装飾と詳細説明だけで、目的・行動・体力・危険・一時停止を消さない。

高さが360px未満では目的を2行に集約し、装飾ロゴと通常通信を畳み、重要通知だけ上部の目的補足へ出す。操作部品とその当たり判定を縮小して解決しない。安全領域を除いた表示領域が横600×高さ320 CSS px未満では「画面を広げる／横向きにする」とポーズ・設定への導線を表示し、窮屈な配置でプレイを開始しない。画面見本は375px高以上の代表レイアウトであり、全設定の組合せの完成品ではない。

最初に安全な船の近くで「移動」「左右を見る」「E／調べる」の3つを実際の入力で確認する、スキップ可能な短い練習を置く。ルートの解答は教えず、目的と操作を伝える。船では点火前に「上昇→北のゲート」の説明を出す。

## 6. 実装契約

入力アダプター → 正規化フレーム → 移動／戦闘／強奪／船 → 読み取りモデル → HUD、という経路にする。

```ts
// 新設する契約の設計例。現行コードに実装済みの型ではない。
type InputFrame = {
  move: { x: number; y: number }; // -1..1、長さ最大1
  lookRadians: { yaw: number; pitch: number }; // このフレームの角度差分
  held: ReadonlySet<Action>;
  pressed: ReadonlySet<Action>; // 立ち上がり1回
  source: 'keyboard' | 'mouse' | 'touch';
};
```

- 矢印は角速度×deltaTime、マウス／タッチは差分×感度で角度へ変換。ピクセル入力に再度deltaTimeを掛けない。非アクティブ時の差分を蓄積しない。
- InputRouterは同時入力を足し過ぎない。移動軸は操作中の所有者1つ、押下は入力源ごとに保持し、他入力源のkeyupで解除しない。モード変更時に全解除。タッチ表示とpointer lockモードは設定の明示選択を優先する。
- CameraControllerに視点処理・補助・水平復帰を集約。ゲームルール側はDOMを参照しない。
- InteractionResolverが選んだIDをHUDと実行側で共有し、表示と実行の不一致を防ぐ。
- HudViewModelが目的、状態、操作可能性、active-deviceラベルを生成。通信中のキー直書きは段階的に置換する。
- メニューは意味のあるHTMLボタンを使用し、フォーカスを閉じ込めて終了後に適切な操作先へ戻す。頻繁な視点変化をaria-liveで読み上げず、目的変更・危険・保存結果のみ通知する。
- ミッション保存のスキーマ1を維持。設定は別キーのv2へ移行し、旧volume/sensitivity/quality/reducedMotionを引き継ぐ。操作中pointerIdや押下を保存しない。
- 会話中を含めvisibilitychange/pagehideで入力解除・安全なチェックポイント保存。復帰は停止画面から再開。復帰ボタンの操作で音声を再開する。

## 7. スマホの描画・配信

Mobile Lowを初期選択にし、実機で余裕が確認できた端末からMediumを提案する。自動品質変更は解像度・装飾だけを変え、視認すべき敵・扉・心臓・船は消さない。

| 初期調整値 | Mobile Low | Mobile Medium |
|---|---:|---:|
| 描画DPR（devicePixelRatioと別） | 0.65 | 0.85 |
| 動的影 | OFF | 原則OFF |
| 装飾パーティクル | 最大6 | 最大12 |
| 同時音数 | 最大4 | 最大6 |
| ゲームプレイの最遠方 | 脱出ゲートを含む140mを確保 | 同左 |
| 装飾描画距離 | 65m | 85m |

既存low設定のfar=85をそのまま使って重要目標まで消さない。ゲームプレイの視認距離と装飾LODを分離する。追加の最終アートを量産する前に、CPU/GPU/転送/メモリを切り分けて測定する。

目標（測定結果ではない）：Mobile Low平均30 FPS以上・1% Low 24 FPS以上、PC基準平均60 FPS目標。1% Lowは遅い1%のフレーム時間平均をFPSに換算し、平均FPSとは別に記録する。初回操作可能まで5秒目標（端末・回線・キャッシュ有無を記録）。初期転送20MB未満。最大フレーム時間、draw calls、triangles、可能な範囲でメモリ、連続2周時の発熱・性能低下も記録する。

まず同一ビルドをスマホWebで検証する。スマホからPCの127.0.0.1へはアクセスできないため、実機検証用の到達可能なURLを別途用意する。PWAはHTTPS環境と必要アセットのキャッシュ検証を終えてから出荷。更新版はプレイ中に強制反映せず、保存後の再起動時に切り替える。初回オフライン・キャッシュ失敗・容量不足には復旧説明を出す。ネイティブ化・ストア登録はこの設計変更の対象外。

## 8. 実装順と合格条件

| 段階 | 変更箇所 | 合格条件 |
|---|---|---|
| A キーボード完結 | input.ts、App.tsx、Scene.tsx、MissionHUD.tsx、combat.ts | マウス・開発用look補助なしで新規開始→4ルート→結果→再プレイ。会話・設定・復帰もキーボードのみ |
| B UI可読性 | style.css、MissionHUD、Results、メニュー、入力ラベル | 1440×900・1000×900で本文16px以上、200%ブラウザ拡大でメニュー欠落なし、フォーカス可視 |
| C タッチ | TouchControls、InputRouter、設定v2、対象選択 | 左右利き・標準/125%で4ルートをタッチイベントだけで完走。2指同時操作、cancel、回転、復帰を確認 |
| D 軽量化とPWA | quality presets、描画、アセット・キャッシュ・更新 | 実機の性能・連続2周・読み込み・オフライン再訪・更新互換。PCと保存互換を回帰確認 |

### 必要な証拠

- 自動テスト：矢印回転が30/60/120fpsで同じ角度、斜め速度、押下解除、フォーム入力抑止、pointer lock拒否、射撃キー、対象と実行ID一致、遮蔽、設定移行。
- UI：844×390、667×375、740×360とノッチを模した余白、縦390×844。安全領域内・ボタン間8px・当たり判定重複ゼロ・目的/危険/操作の重なりゼロ。標準/大きめ、左右利き、運搬/飛行/会話も確認。
- 自動通し：既存の開発用視点設定に頼ったPCテストだけでマウス不要と判定しない。実入力のキー・タッチだけで4ルート各1回以上、代表取引は3回連続完走。テレポートやmission注入なし。
- 実機：ノッチ付きiPhone Safari、古めのiPhone Safari、中価格帯Android Chrome、低メモリAndroid Chromeを候補とする。実際の機種・OS・ブラウザ・解像度・DPRを試験開始時に記入し、未試験は未対応ではなく「未確認」とする。
- ヒューマン：初見の人が2分で目的と操作を説明できる、ミスタップ・照準の疲労・文字を読む距離を観察。端末・操作方法別に記録。
- 工程ごとにbuild/lint/unit/影響E2E、画面見本ではなく実ゲームの画像・動画・計測を残す。利用量・費用はツールで取得できた実測のみ記録し、推定を実測と表記しない。

PCでの60 FPS記録はスマホ性能の証拠にしない。実機が用意できない項目は「未確認」と理由を記録して、モバイル出荷完了とは表現しない。
